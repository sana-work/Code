Text-to-Embedding — E2E Architecture & Interactive PoC

A lightweight stateless embedding-generation use case. The platform reuses the existing synchronous orchestration path, dispatches one high-level Text-to-Embedding step, and keeps embedding-specific behavior inside a reusable tool. Internal orchestration and executor call-stack details are intentionally hidden from this PoC view.

Recommended pattern

Reuse the existing sync execution path

The platform should treat Text-to-Embedding as another synchronous use case. Orchestration remains generic, the executor remains generic, and the new reusable tool owns model-specific embedding preparation and validation.

Use Case→ Sync API→ Execution Platform→ Embedding Agent→ Embedding Tool→ Approved Model
Separation of responsibilities

Keep the architecture clean

  • Platform: auth, config, guardrails, timeout, dispatch and response lifecycle.
  • Agent: thin use-case wrapper that invokes the tool.
  • Tool: validation, normalization, optional address parsing, model invocation and vector checks.
  • Model adapter: approved provider/model integration.
General text

One text → one vector

Company names and short text are normalized and embedded without address parsing.

Address mode

Full address + components

For address inputs, generate the full-address vector plus available street, city, postcode and country vectors.

Out of scope

Generation only

No persistence, Neo4j, cosine search, ranking, entity matching or custom model training in this PoC.

Endpoint approach

Existing Sync API first

The draft POST /v1/embeddings contract can remain a business-facing payload or optional facade. The actual platform execution should still flow through the existing synchronous orchestration capability.

Key design choice: avoid creating a second embedding-specific orchestration service.
Open design items
  • Approved embedding model.
  • Supported dimensions.
  • Long-text policy.
  • Address parser choice.
  • Batch failure behavior.
  • Timeout and performance SLO.
