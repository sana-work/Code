Why Command Center

From scattered data and SQL expertise to one governed interface

Current challenge

Business and operational data is distributed across case, history, AI insights, NLP, API log and external KPI sources. Users often need to know the correct source, table, column and SQL logic before they can answer a business question.

Multiple source systems
Manual query creation
Inconsistent KPI interpretation
Schema names are not business friendly

PoC objective

Provide a single Chat UI that uses governed metadata and controlled query intelligence to answer business questions safely and concisely.

Natural-language questions
Approved metadata only
Validation before execution
Auditable read-only access
IN

In scope now

Chat UI, metadata discovery, single-table query generation, validation, execution, summarization and auditability.

→

Controlled expansion

Additional KPIs, verified relationships and external data sources are introduced only after data-owner validation.

F

Future state

A faster, simplified agentic chatbot on Oracle with fewer agents, conditional sampling, and optional generated reports with graphs, tables and downloadable data.

Metadata & Data Foundation

The chatbot is grounded by three approved metadata objects and targeted data evidence

A

AI_AGENT_METADATA

Search-friendly consolidated metadata exposed to the metadata retrieval flow.

C

AI_COLUMN_METADATA

Technical/business descriptions, display names, normalized names, synonyms and semantic context used to map business language to physical fields.

T

AI_TABLE_METADATA

Table-level business purpose, row grain, date context and synonyms used for table selection.

Metadata quality directly impacts SQL quality

Physical names alone are not enough. Column descriptions should explain the business meaning and how the field is populated or used.

Recommended column enrichment: display_name • normalized_name • business_description • synonyms • semantic_type • selectable/filterable flags.

Future State

Faster Oracle-backed chatbot with fewer, more capable agents

1

Reduce agent hops

Consolidate the current nine-step PoC into four focused agents to reduce orchestration overhead and improve end-to-end response time.

2

Make sampling conditional

Remove the dedicated sampling agent. Use targeted sampling only when metadata confidence is insufficient or value evidence is required.

3

Move execution to Oracle

Adopt Oracle-compatible query generation, deterministic validation and a read-only Oracle execution connection.

4

Add optional report rendering

Successful query results can feed a report service for KPI cards, charts, tables and downloadable data without adding another core agent hop.

Definition of success

Natural-language questions resolve correctly
Only approved schema objects are used
Validation blocks unsafe SQL
Read-only execution is enforced
Answers match query results
Activity is auditable

Guiding principle

Ground questions in governed metadata, minimize unnecessary agent hops, sample data only when needed, validate before execution, and preserve a clean path to Oracle and richer report experiences.
