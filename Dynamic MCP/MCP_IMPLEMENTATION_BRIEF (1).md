# Dynamic MCP Server implementation brief for GitHub Copilot or Devin

## Assignment

Extend the existing `181229.genaiservices.dynamic-mcp-server` repository with a versioned standards package. Release 1 must demonstrate the same registration and invocation requirements on one existing PostgreSQL-backed provider tool and one existing standalone FastMCP server. Use the existing row format and runtime for Dynamic MCP. New Python functions may use a decorator. Existing functions may adopt the package through a reviewed policy mapping keyed by their registered tool identity.

**Start in the existing checkout.** Read its instructions, `docs/IMPLEMENTATION.md`, dependency lock, startup code, tests, and Helm chart. Record the checked-out revision and run the relevant baseline tests. The source for this brief was a set of implementation-reference screenshots and an architecture discussion. The code and lockfile establish actual signatures, field names, dependency versions and test commands. The branch visible in the screenshots was `feature/ARCH-54053-Dynamic-Tool-Registrations`. Use the assigned working branch and preserve collaborators’ changes.

**Release 1 assignment.** Implement phases 1–3 and run the Release 1 checks in section 7. Make verified caller identity and delegated subject propagation the first runtime milestone. Exercise the existing provider tool through its real MCP entry point and adopt the package in one existing standalone server. Use synthetic identities, test upstreams and a disposable configuration store. Follow the repo’s normal review workflow.

**Later release.** Phase 4 describes an optional OpenAPI importer that reduces authoring effort. Schedule it separately after the Release 1 pilot. A valid, manually authored Postgres row is sufficient for every Release 1 acceptance check.

## 1. Architecture and current implementation

Orchestrator owns workflow decisions and agent configuration. Agent Executor runs agent steps. The agent’s MCP client discovers tools and calls the chosen server. Dynamic MCP owns tool registration, tool-specific validation and downstream calls. Keep business endpoint mappings in the tool definition. Keep outbound host approval, CA bundles and reusable credential references under environment ownership. Use the existing agent configuration and client integration for discovery. Change an Executor integration only if the actual client needs a supported way to pass verified request context, and identify that dependency separately.

| Existing location | Documented behavior to reuse | Integration point |
|---|---|---|
| `dynamic_mcp_server/models/compact_tool_config.py` and `models/dynamic_tool_config.py` under the package | `compact_http_v1` and `compact_provider_v1` expand into strict `DynamicToolConfig`. Unknown fields are rejected. Config checks connect declared inputs, policies, operations and output fields. | Add typed governance metadata at the compact and expanded boundaries. Route both through the shared contract validator. |
| `dynamic_mcp_server/db/tool_config_store.py` | Reads existing `gssp_agentic.tool_config`. Looks under `tool_metadata.dynamic_tool_config`, skips unrelated rows, selects published/enabled tools, checks duplicates and builds a revisioned snapshot. | Reuse payload expansion and validation for pre-publication checks. Preserve the shared table and existing row envelope. |
| `dynamic_mcp_server/tools/dynamic_tool.py` | `DynamicTool.from_config()` builds agent-visible schemas and hints. `run()` invokes `RuntimeExecutor`. `register_snapshot_tools()` preflights the batch and rolls back partial registration failures. | Validate each tool’s effective policy before registration and attach safe public metadata. Scope any policy registry to its server and the same snapshot lifecycle. |
| `dynamic_mcp_server/runtime/validation.py`, `runtime/executor.py`, `runtime/http_client.py` | `validate_arguments()` applies field and cross-field rules. `RuntimeExecutor` dispatches `http` or `provider_query` under a deadline. `ProfiledHttpClient` owns outbound calls, TLS clients, credential resolution, token caching and a single client-credential refresh on 401. | Reuse these paths. **Current boundaries.** A PostgreSQL change takes effect at process startup. An invalid published configuration can prevent a pod from becoming ready. There is no documented authoring API or runtime refresh. The external route is disabled pending COIN integration. The document describes structured logs and correlation IDs, with advanced metrics, tracing and general retry policies deferred. The provider supports one paginated filter API shape. HTTP definitions support one to five ordered GET/POST operations, including named outputs. These are compatibility inputs for the work below.

## 2. One standards package, two registration paths

Create a versioned, importable Python package using the organization’s existing packaging conventions. A package in this repo with an independently installable distribution is a suitable first implementation if there is no existing shared SDK. Standalone servers must be able to install it without starting Dynamic MCP, loading a PostgreSQL configuration, or acquiring its database credentials. Use the repo’s pinned FastMCP and Python versions. Scope compatibility claims to versions tested in CI.

| Responsibility | PostgreSQL-backed tool | Handwritten FastMCP tool |
|---|---|---|
| Definition | Read compact/full configuration and derive a shared tool declaration from `DynamicToolConfig`. | Derive the declaration from a new function’s `@governed_mcp_tool(...)` metadata or from a reviewed policy mapping plus the registered schema of an existing function. |
| Registration | Validate the declaration inside `register_snapshot_tools()` and attach it to the native `DynamicTool`. | Register a new decorated function once. For an existing handler, bind policy to its existing registration. Validate the final catalog, including tools registered directly or through supported extensions. |
| Per-call enforcement | Shared middleware resolves the actual tool/version and applies its policy before `DynamicTool.run()`. | The same middleware resolves the standalone tool and applies its policy before its handler. |
| Execution | Existing `RuntimeExecutor` and `ProfiledHttpClient`. | Existing business handler. For API wrappers, use an approved client with equivalent outbound controls. Reuse the profiled client where dependencies permit. |

Install the package once in each server’s assembly function. At startup, reconcile policy bindings against every tool that can be exposed. Before adding a server to the platform’s approved endpoints, run a platform-owned CI/onboarding check against the candidate server and record its release or image revision. Inspect the published schemas and exercise discovery and direct invocation with authorized and denied test principals. Metadata stamped by the server is insufficient evidence on its own. Run the gate again when the server release or its policy bindings change.

**When to revisit a service.** A gateway adds value when the platform must control traffic to independently managed servers and can require all managed callers to use that gateway. Consider a central policy decision service when entitlement changes must take effect across pods immediately and the existing identity platform cannot meet that requirement. For this release, execute checks inside each server process.

## 3. Phase 1 — Define minimum standards and preserve existing callers

Implement one shared declaration model and validator. Use stable rule codes and return the tool name, field path, rule and correction. Collect violations for authoring and CI. At serving time, enforce the existing all-or-nothing startup behavior. An author may select an approved access policy or add restrictions within their authority. The deployment owns the minimum policy for a server or tool family.

| Area | Rule to implement |
|---|---|
| Naming and documentation | Require a stable name, a useful purpose, meaningful descriptions for inputs and outputs, and routing guidance when sibling tools overlap. For new Python functions check typed business inputs, documented arguments and return semantics. Reject unrestricted `**kwargs` and untyped public payloads unless explicitly modeled as a supported content type. For database rows validate equivalent metadata. Generic auto-generated descriptions such as “Gfcids.” deserve an actionable lint finding. |
| Ownership, shape and effect | Record owner or owning domain, contract version, access policy and whether the tool reads or mutates data. Collections, single entities and mutations need appropriate validation. Support the existing named multi-operation result. Derive public MCP hints from reviewed semantics. A count/search implemented with POST can be read-only. |
| Strict filters | Expose only supported fields, types, enums where known, date bounds and allowed combinations. Reject unknown arguments before downstream work. Preserve aliases only as supported by the current client contract. Validate both advertised schemas and runtime behavior. |
| Pagination and output | Bound collection requests and result size. Preserve existing provider `limit`, `offset`, `requested_fields`, maximum limit and `records` output. Reject an invalid limit consistently with the existing executor. For new cursor-backed APIs expose a cursor only when a real continuation mapping is supported. For an oversized or truncated upstream response, return an explicit error or documented continuation. Never report a collection complete solely because a local slice was taken. |
| Column projection | Keep the selectable field allowlist and lean defaults. Enforce declared types and required fields. Omit undeclared upstream fields from every agent-visible representation. Require a stable identifier only for contracts promising follow-up by ID, with upstream permission to see it. Preserve existing field selection semantics for published versions. |
| Runtime and release controls | Bound deadlines and permitted output sizes using deployment ceilings and per-tool limits. Emit safe errors and audit outcomes. Validate published tools against an approved policy. Keep credentials, caller identity and internal connection details out of public schemas and metadata. |

**Migration.** Inventory existing published rows, full and compact formats, standalone tools, and representative `tools/list` and `tools/call` results. Produce a read-only compatibility report before rollout. Backfill required governance metadata through the normal controlled config process. Where access policy or mutation behavior cannot be inferred reliably, require an owner-supplied mapping before enabling the governed release. Do not invent permissive defaults for old rows. Verify the backfill with the old release as well as the candidate: old strict models may reject newly added keys on a pod restart. If so, deploy a reader that accepts the new format first, or version/store the metadata in a location both readers support. Keep an explicitly tested rollback-compatible configuration revision.

**Illustrative parity example.** These are proposed governance fields. Finalize their placement after inspecting the current serializers. A standalone provider wrapper may use `@governed_mcp_tool(..., owner="asset_services", effect="read", policy_ref="asset_events_read")`. The PostgreSQL author supplies the same three values in the tool’s governance block. Both registrations should expose the existing `event_id` input and declared output fields for the example, and resolve the same policy for the same verified caller. The database stores rule references and declarative mappings. Python imports, SQL snippets, templates and executable expressions are outside that format.

## 4. Phase 2 — Integrate identity, runtime checks and upstream API readiness

1. **Authenticate the MCP request.** Locate the approved COIN/service-identity integration and determine which component verifies the immediate MCP caller. The Executor or SDK transport may make the actual network call even when Orchestrator initiated the workflow. Bind actor identity to the authenticated workload. For tools acting on behalf of a person, obtain the subject and any relevant tenant from verified claims or an approved, short-lived, audience-bound delegated assertion. Validate issuer, audience, expiry and caller binding as applicable. Scopes must come from verified context. Keep each request’s principal isolated through concurrent calls and cancellation.
2. **Authorize discovery and direct calls.** Resolve every exposed tool to registered policy. Filter discovery according to that policy and check entitlement again for `tools/call`. An unauthorized direct call must stop before any business upstream call. Keep caller identity, tenant authority and scopes out of model-controlled arguments. A business filter such as `assignee_id` can narrow results within the caller’s entitlement. For provider tools obtain mandatory outbound `X-SOEID` from verified delegated context. Reserve identity headers and reject configs or arguments that override them. Use a distinct authorization rule for legitimate service-only tools.
3. **Use the existing outbound trust path.** Validate final HTTPS destinations, approved auth/TLS profiles, credential purpose and the destinations authorized for each credential. Cover both token and data hosts. Resolve secrets through existing Vault-backed profiles. Use hop-specific credentials or an approved exchange. Keep the current client-credentials cache isolated from any future user-delegated token cache. Preserve the existing disabled external route until the actual inbound integration passes deployment tests. If COIN fixtures or an approved verifier are unavailable, implement and test the interface locally with a test-only verifier and report the production dependency explicitly.
4. **Check API readiness against the tool’s behavior.** For user-scoped APIs verify the upstream enforces record, field and action entitlements. Capture evidence from an integration fixture or approved test environment for two subjects with different access. For collections verify bounded upstream requests and projection. For mutations verify replay behavior, stable logical operation identity across retries and distinct keys across separate intended actions. A correlation ID alone cannot identify a business operation. For a tool with several mutating operations, document partial-failure and replay semantics per operation before enabling retries. Preserve the existing one-time credential refresh where replay is safe.
5. **Expose actionable, sanitized failures and audit evidence.** Distinguish invalid input, denial, conflict, rate limiting and timeout. Return safe recovery information such as an approved retry interval. Keep upstream response bodies, tokens, cookies, raw business payloads and secret references out of agent errors and logs. Follow existing logging conventions. Record authorized audit identifiers for actor and subject, tool/version, correlation ID, outcome and duration. For high-volume or long-running APIs document the upstream quota, per-principal limits where needed, latency budget and any supported job-status operation. Set budgets per use case. Measure latency claims and document where a requirement is enforced across pods.

The readiness validator can check what OpenAPI declares. It cannot prove row-level authorization, upstream deduplication or actual latency. Record these as behavioral checks with explicit evidence. Respect approved legacy auth profiles and equivalent upstream contracts where the platform permits them. A new universal OAuth-only rule would conflict with the documented cookie and secret-header profiles.

## 5. Phase 3 — Deliver the decorator, standalone integration and conformance CLI

**New tools.** Implement `@governed_mcp_tool` as a thin adapter over the common declaration and registration functions. Reuse native schema generation or explicit supported schemas for the installed FastMCP version. Dynamic MCP calls the same registration API for each native tool instance. Preserve the existing execution path and derive authorization from a trusted server-local binding.

**Existing standalone tools.** Load a reviewed mapping when the server starts. Scope it to the server and key it by the actual registered name and version where the server supports versioning. For example, a mapping for an existing `list_events` handler can supply `owner=asset_services`, `effect=read` and `policy_ref=asset_events_read`. Read its input and output schemas from the actual registration. Keep the same handler, tool name and call signature. This mapping supplies policy metadata only. The resulting declaration goes through the same schema and policy validation as a decorated tool.

At startup reject missing policies, stale mapping entries, conflicting declarations and unresolved policy references. Report the affected tool and corrective action. When migrating a mapped handler to the decorator, remove its mapping in the same change. Verify that an ordinary MCP call reaches the handler exactly once. Run this check on the effective catalog that the server will expose.

Release 1 delivers `validate-config` and `validate-server`. The table also identifies the later importer. These names are proposed command interfaces.

| Operation | Input and output |
|---|---|
| `validate-config` | Read a candidate compact or full tool row and target trust profile. Expand it and run the same strict, governance and preflight checks used by startup. Report all safe-to-collect findings. A check performed without environment-specific trust evidence must identify which checks are outstanding. |
| `validate-server` | Run source/registration checks for local Python servers and protocol checks against a running MCP endpoint. Report missing or inconsistent tool metadata, schemas, bounds and public identity fields. Use a suitable test principal for each view of the catalog. |
| `import-openapi` (later release) | Generate a reviewable draft row or draft bundle using the phase 4 rules. Default to a local output artifact, with publication performed through the existing controlled process. |

Integrate a pinned MCP Inspector CLI or compatible official SDK client into CI. Check the installed CLI help and dependency lock before selecting flags, transport, and exit-code handling. Exercise `tools/list` and `tools/call` against the real mounted HTTP route and inspect MCP-level `isError` and structured content. Inspector’s schema checks complement the platform-specific rules. Audit schema references, nested objects and arrays for exposure of trusted inputs. Check both structured content and any text representations. Keep Inspector and its Node dependencies outside the serving image.

Pilot with one existing provider-query tool and one existing standalone FastMCP server. For the standalone pilot, exercise a currently registered handler using the reviewed mapping and cover the decorator in a focused test. If the standalone checkout is unavailable, complete the shared package and Dynamic MCP work and exercise both adapters on a reference server. Record the missing real-server pilot as an open Release 1 acceptance item. Apply the same distinction to test identity fixtures and the approved COIN deployment integration.

## 6. Phase 4 — Optional later release: OpenAPI-assisted authoring

Implement an authoring-only importer for an explicitly selected OpenAPI operation or reviewed group of operations. Take a local OpenAPI file and a small manifest specifying the tool’s purpose, routing guidance, selected operations, input/output mappings, applicable pagination, effect, ownership and policy. Resolve reusable schemas from approved local inputs. Report unsupported or unresolved references with the operation and source location. Block automatic publication for ambiguous mappings.

- Import generic REST operations into `compact_http_v1` when representable. Generate `compact_provider_v1` only for the supported provider filter API and when the service identifier, column mappings and connection metadata are supplied. Preserve operation order and named output mappings for multi-operation HTTP tools.
- Classify every path, query, header and body input. Allowlist business inputs. Bind caller identity, credentials, tracing and idempotency through trusted runtime context. Reject collisions with reserved inputs or headers. Map declared upstream enums, constraints, projection and pagination only when the runtime actually enforces them. Unsupported HTTP verbs, nested schema forms or cursor semantics must produce a precise diagnostic, or an explicitly scoped runtime enhancement with tests.
- Emit a draft under `tool_metadata.dynamic_tool_config` using actual row columns and serialization from `ToolConfigStore`. Default to unpublished, credential-free definitions referencing approved profiles. Produce deterministic output. Each draft should expand into the existing strict model when evaluated as a prospective published tool. The validator must exercise the publication path even though the loader correctly skips drafts during ordinary startup.
- Prove the lifecycle using a disposable database: import, validate the candidate, insert a draft with the existing write mechanism, confirm it stays hidden, publish the validated revision, restart the test server, discover and call it. Validate the resulting candidate catalog for duplicates and conflicts; a successful single-row check is insufficient. Use the platform’s version/transaction controls when introducing a publish action so validation and publication refer to the same candidate. Report live refresh as a separate follow-up if requested.


## 7. Release acceptance and handoff

**Release 1 exit criteria.** Run the following paired checks through MCP on the existing provider tool and the standalone pilot. Record the server revision, policy binding, test principal role, MCP outcome and upstream or handler call count. Use test identities and redact sensitive identifiers.

1. An invalid declaration fails validation before the tool can be served. Equivalent defects yield the same shared rule code on both paths.
2. A denied principal cannot discover the restricted tool. Calling it directly by name is denied, with zero business handler or upstream invocations.
3. An authorized principal can discover and invoke the tool. The provider receives the SOEID from verified context. The result includes only fields allowed by the output contract and the caller’s entitlements. Use distinct test subjects to confirm upstream access boundaries and inspect all agent-visible representations.

**Worked provider fixture.** Use a synthetic tool named `query_sample_events` with the existing ten-digit `event_id` input mapped to upstream column `CORP`. Configure an allowed output named `event_id` mapped to the same column. Have the mock provider return `{"PagedList":[{"CORP":"0000000042","INTERNAL_NOTE":"fixture-only"}]}`. With a verified test principal, call the tool with `{"event_id":"0000000042","requested_fields":["event_id"],"limit":1,"offset":0}`. Assert that the request selects `CORP`, carries the SOEID from the verified context, and returns structured content `{"records":[{"event_id":"0000000042"}]}`. This case checks string identity with leading zeros, column mapping and projection together. Use a second HTTP fixture with a read-only POST and named count/details outputs to cover behavior the provider fixture cannot exercise.

Run existing test suites before and after changes. Add focused regression tests for the shared package and both registration paths. Run importer-specific tests with the optional later release. Use maintained fixtures containing synthetic identities and endpoints. Capture the exact commands and dependency versions from the actual project.

| Scenario | Required evidence |
|---|---|
| Existing catalog | Prior compact and fully expanded rows still load after migration. Unrelated rows are skipped. Existing provider input/output names and named HTTP envelopes match captured schemas and representative results. |
| Failed startup | Duplicate, invalid or unapproved published tools fail the snapshot. Simulated add failure removes tools and policy bindings added by that pass. `/ready` cannot succeed on a failed startup. |
| Shared minimum standard | Validate Postgres, decorated and mapped declarations. Catch unbound tools and stale or conflicting mappings. A mapped standalone tool runs exactly once without a database connection. |
| Input/output boundaries | Unknown filter, invalid range, out-of-range page, unknown column and undeclared identity override are rejected. Large collection responses stay bounded. A local filter cannot substitute for upstream access control. |
| Identity and authorization | Exercise the managed HTTP route with and without valid service/delegated context. Denied tools are hidden and direct invocation is denied before dispatch. Two authorized subjects see only their entitled data for list and ID lookups. Concurrent requests retain their own identities. |
| Writes and errors | Where mutations are supported, retrying the same logical action once has one upstream effect. Two distinct actions with the same payload remain distinct. Model-visible failures and logs exclude raw upstream content and credentials. |
| Release 1 deployment | Helm tests cover existing mounts, route policy and both slash forms. Record catalog revisions during the pilot rollout where available. The onboarding gate records the tested server revision and allow/deny evidence. |
| Later importer acceptance | A supported OpenAPI fixture yields a valid draft and a callable published tool after restart. Unsupported mappings produce actionable diagnostics. |

**Handoff from the coding agent.** Provide a changed-file summary, package installation instructions, one decorated example, one reviewed mapping for an existing handler, and one valid Postgres definition with its expected call and result. Include the compatibility/backfill and rollback procedure, test results, evidence from both pilots and the platform onboarding decision. List unresolved production dependencies such as COIN verification, upstream entitlement evidence or access to a standalone checkout. Update the implementation reference with shipped behavior. Track the optional importer, hot reload and static code generation separately.
